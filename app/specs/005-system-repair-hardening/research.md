# Research: System Repair & Hardening

> **Feature**: specs/005-system-repair-hardening
> **Date**: 2026-07-12

## R1: Permission Key Naming Convention

**Decision**: Use `{action}_{entity}` pattern (e.g., `add_student`, `edit_student`, `delete_student`)

**Rationale**: The existing codebase already uses this pattern in Spatie Permission middleware (e.g., `permission:add_student`). All 20 existing Form Requests return `true` in `authorize()`, so there's no conflicting convention. Using the same pattern avoids renaming existing permissions and ensures consistency between middleware and policy checks.

**Alternatives considered**:
- `{entity}.{action}` dot notation — more Laravel-idiomatic but requires renaming all existing permissions
- `permission_{action}_{entity}` — overly verbose, no existing precedent

## R2: CSP Policy Configuration

**Decision**: Practical CSP with `unsafe-inline` for scripts and styles

**Rationale**: The application uses Blade templates with inline `<script>` and `<style>` tags, plus Alpine.js which requires inline event handlers. A strict CSP would break the entire frontend. The practical policy still blocks external script injection, clickjacking via foreign frames, and data exfiltration to untrusted origins.

**CSP String**: `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:`

**Alternatives considered**:
- Strict CSP (`script-src 'self'`) — would break all Blade/Alpine inline code
- Report-only CSP — monitors without enforcing, delays security benefit
- Nonce-based CSP — requires significant Blade template refactoring

## R3: Route Method Migration Strategy

**Decision**: Direct replacement — convert GET destroy → DELETE and POST update → PUT, updating all Blade forms with `@method()` directives

**Rationale**: The frontend is server-side rendered Blade + Livewire (not a separate SPA). All route calls are generated by Blade's `route()` helper and `{{ Form:: }}` or `<form>` tags. Converting methods is safe because:
- Blade's `@method('DELETE')` and `@method('PUT')` directives handle HTML form method spoofing
- No external API consumers are documented
- Livewire components use `wire:click` which maps to POST internally (not affected by route method changes)

**Alternatives considered**:
- Gradual migration (add new routes, deprecate old) — unnecessary complexity for server-rendered app
- Keep old routes as aliases — adds maintenance burden with no benefit

## R4: Service Layer Architecture

**Decision**: Extract 5 service classes from 5 oversized controllers, plus a base `executeInTransaction()` wrapper

**Rationale**: Current controller sizes:
- ReceiptPaymentController: 506 lines (target: <250)
- StudentsController: 503 lines (target: <250)
- HomeController: 493 lines (target: <200)
- FeeInvoiceController: 298 lines (target: <250)
- UserController: 243 lines (already near target)

22 occurrences of `DB::beginTransaction()` across 12 controllers indicate transaction management is scattered. A unified wrapper reduces duplication and ensures consistent error handling.

**Existing services to preserve** (not refactor):
- `FinancialService` (369 lines) — already extracted, handles financial operations
- `InventoryService` (529 lines) — already extracted, handles inventory CRUD
- `CacheService`, `PromotionService`, `StudentRegeister`, `StudentImportService`, `AgeCalculationService` — small, focused, working

**Alternatives considered**:
- Refactor existing services — they're already well-structured
- Use Action classes instead of services — inconsistent with existing patterns

## R5: Policy Authorization Pattern

**Decision**: Create 8 Policy classes with `{action}_{entity}` permission checks, registered in AuthServiceProvider

**Rationale**: The system uses `spatie/laravel-permission` with existing role/permission infrastructure. Currently:
- 0 Policy classes exist
- All 20 Form Requests return `true` in `authorize()`
- Authorization is only enforced at route level via `permission:` middleware

Adding policies provides defense-in-depth: even if middleware is bypassed, the policy catches unauthorized actions. Form Request `authorize()` methods will check `$this->user()->can('add_student')` etc.

**Alternatives considered**:
- Gate closures in AuthServiceProvider — less reusable, harder to test
- Middleware-only approach — already exists but insufficient (no controller-level checks)

## R9: Database Index Strategy

**Decision**: Add indexes on 3 high-frequency query columns via a single migration

**Target columns**:
- `student_accounts.type` — filtered in student account lookups
- `activity_logs.action` — filtered in activity log listing
- `inventory_items.category` — filtered in inventory item listing

**Migration approach**: Single migration file with 3 `Schema::table()` calls, each adding an index. No data modification needed.
