# المتبقي بعد إعادة الفحص — 5 نقاط للإغلاق

> **السياق:** من أصل 44 بند، حوالي 34 (≈77%) اتصلحوا فعليًا ومتحقَّق منهم بفحص الكود مباشرة، بما فيهم أخطر بند (`DB::commit()` الميت). الباقي هنا فقط.

---

## 1. حذف العفو — قيد عكسي يتيم بدون سياق 🔴 أولوية قصوى

- **الملف:** `ExceptionFeesController.php` — دالة `destroy` (السطور 256-276)
- **المشكلة:**
  ```php
  foreach ($studentAccounts as $account) {
      $account->create(['Debit' => $account->Credit, 'Credit' => $account->Debit]);
  }
  ```
  `$account->create()` بيتنفذ على instance موجود مش على الكلاس (`StudentAccount::create()`)، فالسجل الجديد بيتكوّن **بدون** `student_id`, `exception_id`, `grade_id`, `academic_year_id`, `type`, `school_id`. يعني قيد عكسي بيتسجل في دفتر الطالب لكن من غير أي سياق يوضح هو عكس أنهي عملية. نفس نمط الخطأ اتصلح في `AccountingReversalService` (بند 28 في الفحص السابق) لكن اتنسى هنا في المتحكم.
- **الحل:** استبدال الاستدعاء الحالي باستخدام `AccountingReversalService` (نفس الخدمة اللي بتعمل الـ reversal الصحيح في باقي المسارات)، أو لو مفيش داعي لخدمة منفصلة، نسخ كل حقول السياق من `$account` الأصلي صراحة في استدعاء `StudentAccount::create([...])` جديد بدل الاعتماد على `$account->create()`.

## 2. اتجاه قيد الصرف في `fund_accounts` — يحتاج تأكيد فعلي 🔴 أولوية قصوى

- **الملفات:** `PaymentService.php` (S65-71 — القبض)، `AccountService.php` (S154 — الصرف)، `ExchangeBondController.php` (S119 — التعديل)
- **المشكلة:** القبض والصرف الاتنين بيسجلوا في `fund_accounts` بنفس الاتجاه (`Credit = amount, Debit = 0`)، رغم إنهم عمليتين معاكستين محاسبيًا (المفروض واحدة تزود الخزنة والتانية تنقصها). بالإضافة، `ExchangeBondController::update` (S119) بيحط `Debit = amount` بينما `store` بيحط `Credit = amount` لنفس نوع العملية — يعني إنشاء سند صرف وتعديله بيسجلوا الاتجاه بشكل مختلف عن بعض.
- **الحل:**
  1. تحديد الاتجاه الصحيح محاسبيًا أولاً: القبض بيزود رصيد الخزنة (Credit)، الصرف بينقصه (Debit) — أو العكس حسب الاتفاقية اللي شغالين بيها في باقي النظام، المهم يبقوا معاكسين مش متطابقين
  2. تصحيح `AccountService.php:154` ليستخدم الاتجاه المعاكس للقبض
  3. تصحيح `ExchangeBondController::update` ليطابق نفس الاتجاه المستخدم في `store` بالظبط
  4. **قبل قفل البند ده**: عمل اختبار يدوي حقيقي — سجّل عملية صرف واتأكد إن رصيد الخزنة النهائي فعلاً نزل بمقدار المبلغ، مش زاد

## 3. صفحة تعديل سند الصرف بتعرض الوصف فاضي

- **الملف:** `exchange_bond/edit.blade.php` — السطر 28
- **المشكلة:** `value="{{ $exchange->note }}"` — العمود الفعلي في الجدول اسمه `description` مش `note`، فحقل الوصف بيظهر فاضي دايمًا في صفحة التعديل رغم وجود بيانات محفوظة فعليًا.
- **الحل:** استبدال `$exchange->note` بـ `$exchange->description` في نفس السطر.

## 4. تعديل المرحلة الدراسية ممكن يفشل بصمت

- **الملفات:** `GradeStoreRequest.php` (قاعدة الـ validation) + `GradesController.php` — السطر 133
- **المشكلة:** لما اتصلحت مشكلة "الإنشاء مستحيل" (بند 10 قديم)، تم حذف `id` من الـ validation بالكامل بدل فصله بين حالة الإنشاء والتعديل. لكن `GradesController` (S133) لسه بيقرأ `$request->id` في مسار التعديل. لو الـ `id` مش جاي فعليًا في الـ request (لأن الـ validation مبقتش بتفرضه)، التعديل ممكن يفشل أو يتصرف بشكل غير متوقع بصمت.
- **الحل:** فصل قواعد التعديل عن الإنشاء بدل قاعدة واحدة مشتركة — إما FormRequest منفصل لكل عملية، أو استخدام شرط زي `'id' => $this->isMethod('put') ? 'required|exists:grades,id' : 'nullable'` جوه نفس الـ Request.

## 5. تعديل العفو — احتمال قراءة خاصية على null

- **الملف:** `ExceptionFeesController.php` — السطور 212-214 (دالة `update`)
- **المشكلة:** `ExceptionFees::where('id', ...)->first()` من غير فحص إن النتيجة موجودة، وبعدها مباشرة `$pay->date = ...` — لو الـ `id` الممرر مش بتاع سجل موجود فعلاً، الكود هيحاول يكتب خاصية على `null` ويطلع Error.
- **الحل:** استبدال `first()` بـ `firstOrFail()` أو إضافة فحص `if (!$pay) { ... }` صريح قبل أي استخدام لخصائصه.
