## 🔴 المرحلة صفر — قبل أي حاجة تانية (نفس الأولوية، خطورة أعلى مما كان متوقع)

### 1. `DB::commit()` كود ميت — عمليات الدفع مش بتتحفظ فعليًا ⚠️ الأخطر في كل التقرير
- **الملف:** `PaymentService.php:98-99` و `182-183`
- **المشكلة:** ترتيب الأسطر `return $report_data;` ثم `DB::commit();` — الـ commit سطر ميت تمامًا، منفّذ أبدًا. المعاملة (transaction) فعليًا **بترجع (rollback) تلقائيًا** بمجرد انتهاء الاتصال، طالما مفيش commit صريح. لو النظام شغال في الإنتاج بالفعل، يبقى إما فيه autocommit مفعّل على مستوى الاتصال (وده بيلغي فايدة الـ transaction بالكامل من الأساس)، أو إن السلوك الفعلي مش موثّق صح.
- **الحل:**
  1. نقل `DB::commit();` ليكون **قبل** `return $report_data;` مباشرة في السطرين (98 و182)
  2. **قبل ما تعمل أي حاجة تانية**، تأكد فعليًا (مش افتراضًا) هل المعاملات بتتحفظ في الإنتاج دلوقتي ولا لأ — افحص إعدادات `autocommit` في `config/database.php` واتصال MySQL. لو لقيت إن فعلاً في بيانات مش محفوظة، ده يستدعي فحص فوري لأي دفعة اتسجلت في آخر فترة
  3. كتابة Feature Test يتأكد إن `student_accounts` و`fee_invoices` فعلاً بيتغيروا بعد استدعاء `handleFeeInvoice`/`handlePartialPayment` كاملين

### 2. `catch (Exception $e)` بدون import
- **الملف:** `PaymentService.php:100,184`
- **المشكلة:** مفيش `use Exception;` في أعلى الملف، فأي استثناء بيحصل جوه الـ try بيسبب Fatal Error بدل ما يتمسك.
- **الحل:** إضافة `use Exception;` (أو الأفضل `use Throwable;` ليمسك كل أنواع الأخطاء) في أعلى الملف.

### 3. الـ catch بيرجع نوع بيانات غلط
- **الملف:** `PaymentService.php:104,188`
- **المشكلة:** توقيع الدالة معرّف يرجع `array`، لكن الـ catch جواها بيرجع `RedirectResponse` → `TypeError` عند حدوث أي استثناء.
- **الحل:** توحيد نوع الإرجاع — إما تشيل الـ return type hint من الدالة، أو تخلي الـ catch يرمي الاستثناء تاني (`throw $e;`) ويتم التعامل معاه في الـ Controller اللي بيستدعيها، مش داخل الـ Service نفسه.

### 4. الوصول لـ `$invoice->student_id` قبل فحص null
- **الملف:** `PaymentService.php:38`
- **المشكلة:** الفلتر `where('student_id', ...)` اتضاف (خطوة صح) لكن مفيش فحص إن الفاتورة أصلاً موجودة قبل الوصول لخاصيتها، فلو الفاتورة مش موجودة → `Attempt to read property on null`.
- **الحل:** استخدام `findOrFail()` بدل `first()`/`find()`، أو إضافة فحص `if (!$invoice) { throw ... }` صريح قبل أي استخدام لخصائصه.

### 5. ربط الإيصال بقيد الطالب لسه مش بيتحفظ

### 6. اسم المتغير خطأ رغم تصحيح المفتاح

- **الحل:** إضافة `school_id` (و`exchange_bond_id` لـ `StudentAccount` تحديدًا) لمصفوفة `$fillable` في الأربعة، وبعدها كتابة test يتأكد إن أي سجل جديد بياخد `school_id` صح تلقائيًا.

### 10. الإنشاء في المراحل الدراسية "مستحيل" رسميًا
- **الملف:** `GradeStoreRequest.php:26`

- **الحل:** فصل قواعد الإنشاء عن التعديل — إما FormRequest منفصل لكل حالة، أو استخدام `sometimes`/شرط `$this->isMethod('put')` عشان `id` يبقى مطلوب في التعديل بس.

### 11. المتحكم لسه بيقرأ اسم الحقل القديم
- **الملف:** `GradesController.php:62`
- **المشكلة:** الـ Blade بيبعت `name` (بعد التوحيد)، لكن الـ Controller لسه بيقرأ `$request->Grade_Name` القديم → القيمة المخزّنة `null` دايمًا.
- **الحل:** تصحيح الـ Controller ليقرأ `$request->name` بدل `Grade_Name`، والتأكد إن الاسم متسق في كل نقاط القراءة/الكتابة لنفس الحقل.

### 12. حذف مرحلة فيها فصول بينجح بالغلط (ثغرة سلامة بيانات)
- **الملف:** `GradesController.php:168-169`
- **المشكلة:** الـ withCount بقى بيقرأ العلاقة الصح (`class_rooms`)، لكن الكود بيتحقق من `$grade->class_room_count` (بالمفرد) — الخاصية دي مش موجودة، فبترجع `null`، و`null == 0` في PHP، فشرط "امنع الحذف لو فيه فصول" بيتجاوز دايمًا. **مرحلة دراسية فيها فصول وطلاب ممكن تتحذف فعليًا.**
- **الحل:** تصحيح اسم الخاصية المستخدمة في الشرط لتطابق اسم العلاقة الفعلي (`class_rooms_count`)، وإضافة test يتأكد إن حذف مرحلة فيها فصول بيترفض فعليًا.

### 13. حفظ رقم ولي الأمر كاسم أب (بيانات تالفة تُكتب فعليًا)
- **الملفات:** `ParentRepository.php:18,21`, `StudentRegeister.php:21`
- **المشكلة:** `'father_name' => $request['parent_id']` — بيحفظ الـ ID الرقمي لولي الأمر في حقل اسم الأب النصي. ده مش باج بيمنع العملية، **ده باج بيكتب بيانات غلط بنجاح** في كل تسجيل جديد.
- **الحل:** تصحيح المصدر الصحيح لاسم الأب (على الأرجح `$request['father_name']` أو الحقل المكافئ من الـ Request مش `parent_id`)، ومراجعة كل السجلات اللي اتسجلت بعد ظهور الباج ده لتصحيحها يدويًا لو أمكن.

### 14. Fatal Error في حذف ولي الأمر من Livewire
- **الملف:** `ParentsTable.php:62`
- **المشكلة:** بيستدعي `$this->logActivity()` لكن الكلاس مش بيستخدم الـ trait `LogsActivity` → Fatal Error عند أي محاولة حذف.
- **الحل:** إضافة الـ trait `use LogsActivity;` للكلاس، أو حذف الاستدعاء لو التسجيل بيتم من مكان تاني بالفعل.

### 15. رسالة "فشل الحذف" بتظهر حتى مع النجاح
- **الملف:** `ParentsTable.php:67-70`
- **المشكلة:** مفيش `else`/`return` بعد نجاح عملية الحذف، فالكود بيكمل تنفيذ ويوصل لرسالة الفشل حتى لو الحذف نجح فعليًا.
- **الحل:** إضافة `return` واضح بعد رسالة النجاح، عشان الكود ميكملش لباقي المنطق.
